# TDD 스터디: 프로젝트에 적용하기까지

공통 예제 하나를 TypeScript로 8주 동안 키워 가며 TDD를 연습하고, 마지막에는 각자 실제 프로젝트에 적용합니다.

- **1~5주:** 공통 예제를 **TypeScript + Vitest**로 진행합니다. 유닛 테스트만 다룹니다.
- **6~7주:** 각자 **자기 프로젝트 언어**로 실제 코드에 적용합니다. 웹은 TS, 모바일은 Kotlin이나 Swift입니다.

---

## 시작하기 (0주차)

Node.js 20 이상이 필요합니다.

```bash
npm install
npm test          # watch 모드: 파일을 저장할 때마다 테스트가 다시 돕니다
```

처음 실행하면 **테스트가 실패해야 정상입니다.** `src/PaymentCalculator.ts`가 아직 없기 때문입니다. 이 빨간불을 확인하는 것까지가 0주차입니다.

| 명령 | 설명 |
|---|---|
| `npm test` | watch 모드로 테스트 실행 |
| `npm run test:run` | 테스트를 한 번만 실행 (CI용) |
| `npm run typecheck` | 타입 검사 |

### 과제 제출 방법
- 매주 `weekN/이름` 브랜치를 만들어 작업합니다. 예: `week2/kyle`
- PR을 올리고, 리뷰할 때는 **테스트 코드부터** 봅니다.
- 커밋은 Red / Green / Refactor 단위로 나눠 주세요. 그래야 리뷰할 때 흐름이 보입니다.

> ⚠️ **회사 코드는 이 레포에 올리지 않습니다.**
> 이 레포에는 1~5주차 공통 예제만 둡니다. 6~7주차 실습은 각자 **회사 레포에서 평소처럼 브랜치를 만들어** 진행하고, 리뷰도 회사 레포 PR에서 합니다. 회사 코드를 복사하거나 붙여넣지 마세요. 스니펫이나 스크린샷도 마찬가지입니다.

## 운영 원칙

1. **1~5주는 유닛 테스트만 다룹니다.** DB, 네트워크, UI는 뒤로 미룹니다.
2. **예제는 하나로 끝까지 갑니다.** 매주 같은 도메인에 요구사항을 하나씩 더합니다.
3. **정답 코드는 없습니다.** 서로 다른 설계를 비교하는 게 목적입니다.
4. **요구사항은 세션을 시작할 때 공개합니다.** 미리 구현해 오지 않습니다.

### 세션 진행 방식 (2시간)
| 시간 | 내용 |
|---|---|
| 20분 | 과제 코드 리뷰. 테스트 코드부터 봅니다 |
| 20분 | 개념 하나 |
| 70분 | 몹 프로그래밍. 드라이버를 5분마다 교대합니다 |
| 10분 | 회고. "이번에 테스트가 내 설계를 바꾼 지점"을 한 줄씩 씁니다 |

## 공통 예제: 시술 예약 결제 금액 계산기

매주 같은 도메인에 요구사항이 하나씩 추가됩니다. **요구사항은 세션을 시작할 때 진행자가 공개합니다.**

---

## 주차별 커리큘럼

### 1주차: Red → Green → Refactor 감 잡기
- **개념:** TDD 사이클, 테스트 목록 먼저 쓰기, 가장 쉬운 테스트부터 시작하기
- **실습:** 요구사항 1. `src/PaymentCalculator.test.ts`의 첫 테스트부터 시작합니다.
- **포인트:** 테스트 하나를 통과시킬 만큼의 코드만 씁니다. 하드코딩도 괜찮습니다.

### 2주차: 좋은 유닛 테스트란
- **개념:** Given-When-Then, 테스트 이름은 "행동과 기대 결과"로 짓기, 경계값, 파라미터화 테스트(`it.each`)
- **실습:** 요구사항 2. 경계값을 찾아 테스트합니다.
- **과제:** 다른 사람의 테스트 이름만 읽고 요구사항을 복원해 봅니다. 복원이 안 되면 이름이 나쁜 겁니다.

### 3주차: 테스트가 설계를 이끈다
- **개념:** 가짜 구현 → 삼각측량 → 명백한 구현, 리팩터링 단계에서 객체 분리하기
- **실습:** 요구사항 3. `if`가 쌓이는 게 느껴지면 객체나 모듈로 분리합니다.
- **포인트:** 리팩터링하는 동안 테스트가 계속 초록불이면 안전망이 제대로 동작하는 겁니다.

### 4주차: 통제할 수 없는 것 다루기 (시간)
- **개념:** 숨은 의존성(`new Date()`, `Math.random()`)을 밖에서 주입하기, 테스트 더블의 종류(Stub / Fake / Mock / Spy)
- **실습:** 요구사항 4. 현재 시각을 밖에서 주입해서 경계 시각을 테스트합니다.
- **과제:** 우리 프로젝트 코드에서 현재 시각을 직접 부르는 곳을 3군데 찾아옵니다.

### 5주차: 협력 객체와 Mock 남용 경계
- **개념:** 상태 검증과 행위 검증의 차이, Fake Repository, "Mock은 내가 소유한 경계에만"
- **실습:** 요구사항 5. `Map`으로 만든 Fake를 사용하고, 협력 객체가 실패했을 때의 상태를 테스트합니다.
- **포인트:** `vi.fn()`으로 호출 순서까지 검증하는 테스트를 일부러 하나 만들어 봅니다. 그런 다음 리팩터링하다가 그 테스트가 깨지는 걸 직접 겪어 봅니다.

> **모바일 개발자 사전 과제 (6주차 전):** 1주차 예제를 자기 언어(XCTest 또는 JUnit)로 30분 안에 다시 풀어 옵니다.

### 6주차: 레거시에 테스트 붙이기 ← 프로젝트로 넘어가는 다리
- **개념:** 특성 테스트(지금 동작을 그대로 고정하는 테스트), Seam(코드를 바꾸지 않고 의존성을 바꿔 끼울 틈), 테스트하기 어려운 코드의 특징
- **실습:** 각자 **회사 레포에서 브랜치를 만들고**, 계산이나 판단 로직이 있는 함수 하나를 고릅니다. 특성 테스트로 감싼 뒤 리팩터링합니다. 이 레포로 코드를 가져오지 않습니다.
- **세션 공유:** 회사 레포를 화면 공유로 띄워 놓고 함께 봅니다.
- **기준:** UI나 API 호출이 섞인 코드라면, 로직만 떼어내는 것까지가 이번 주 목표입니다.

### 7주차: 실제 티켓 하나를 TDD로
- **실습:** 이번 스프린트 티켓 중 하나를 TDD로 구현하고 **회사 레포에** PR을 올립니다. 스터디원은 그 PR에서 리뷰합니다.
- **팀 규칙 정하기:** 테스트 네이밍, 테스트 파일 위치, "어디까지 유닛 테스트로 할지", CI에서 테스트 돌리기

### 8주차: 회고와 다음 단계
- 각자 PR 공유: 잘된 점, 막힌 점, TDD가 맞지 않았던 상황
- **다음 시즌 예고:** 통합 테스트, ATDD/인수 테스트, UI 테스트

## 진행자 체크리스트

- [ ] 리뷰할 때 테스트 코드를 프로덕션 코드보다 먼저 본다
- [ ] 각 주차의 "정답 코드"를 만들지 않는다
